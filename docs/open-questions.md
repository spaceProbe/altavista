Compiled 2026-09-02 against [architecture.md](architecture.md). Each entry names the fork,
what I would default to, and what the answer changes. Answers get recorded inline and the

Changes: which export (C ABI, FMU, gRPC, Python) is built first and whether the kernel is even needed.
   **Answer (2026-09-02): our kernel is the engine.** The C ABI export of the dynamics library is a hedge built in P2, not a driver.

   **Answer (2026-09-02): keep AltaVista, internal only.** Crates `av-*`, proto package `altavista.v1`; gmatviz stays the name of the Python GMAT service lineage.
4. **Team and languages.** Rust for kernel and services, TypeScript for the viewer, Python for authoring and GMAT: acceptable given who will maintain it? Default: yes.
   **Answer (2026-09-02): yes, that mix.**
5. **First demo.** What must the first end-to-end demonstration show, to whom, and by when? This sets P1's exit criteria.
   **Answer (2026-09-02): Design: a DRM on the globe.** A DRM authored in Python, propagated with GMAT dynamics, shown on the custom Three.js globe and in ICRF, reproducible from its config hash; internal audience. Date not yet set.
6. **Licensing of our code.** Proprietary, open source, or mixed? Affects dependency choices (BSL Redpanda, GPL tools) and whether spoore's papers/ADRs are public.

## B. Representation

7. **Internal time.** `int64` nanoseconds on TAI (spoore-compatible, leap-second free) with GMAT's A1/TAI/UTC conversions at the boundary, or GMAT's A1MJD doubles? Default: TAI ns. Changes: every epoch field, replay ordering, sub-microsecond HIL timing.
   **Answer (2026-09-02): int64 ns on TAI.** spoore's `epoch_ns` fields keep their type; CDM v1 declares the scale as TAI; GMAT A1/TAI/UTC conversions happen at the GMAT boundary (A1 = TAI + 0.0343817 s).
8. **Leap-second authority.** GMAT's LSK file, our own table, or the platform clock? Default: one table shipped with the platform, validated against GMAT.
   **Answer (2026-09-02): one platform table, validated against GMAT.** Versioned, IERS Bulletin C sourced, CI test against GMAT's LSK file.
9. **Units.** Metres and SI internally (spoore) with km conversion at the GMAT boundary, or km (GMAT)? Default: SI metres. Changes: every conversion site; wrong choice is a classic mission-loss bug.
   **Answer (2026-09-02): SI metres internally.** km conversion lives only inside the GMAT adapter and is covered by the parity goldens.
10. **Mandatory frames on day one.** ICRF/J2000 equatorial, ITRF/ECEF, ENU/NED at an origin, body-fixed of Earth/Moon/Mars, TEME (TLEs), spacecraft body? Default: those six. Changes: frame service scope and GMAT dependence.
   **Answer (2026-09-02):** ICRF/J2000 equatorial for Earth, Moon, Mars and Sun; ITRF/ECEF plus ENU/NED at an origin; spacecraft and platform body frames; **and RIC (radial, in-track, cross-track) relative frames to support RPO and OSAM.** TEME not required.
   Consequences: the frame registry must allow an *entity* as origin, not only a body, with axes derived from that entity's state (RIC, VNB, LVLH; GMAT realizes these as `ObjectReferenced` axes). RPO/OSAM also means metre-to-centimetre precision in a target-centred view (viewer precision target, question 46), relative-motion dynamics (Clohessy-Wiltshire and full nonlinear relative propagation via GMAT) as first-class models, and eventually multi-body contact and docking, which is a dynamics-domain question (question 21).
11. **Uncertainty on design products.** Do planned trajectories carry covariance (from the STM) always, optionally, or never? Default: optional. Changes: GMAT STM propagation in the loop, message sizes.
   **Answer (2026-09-02): always optional, explicitly requested per DRM.** No profile-specific defaults: the user does not want specialized defaults that make performance inconsistent between profiles. Design rule generalized: *profiles select components, never change model behaviour or numerical settings*; anything that affects results is declared in the DRM or system definition and hashed.
12. **Non-Gaussian beliefs.** Spoore's rule is Gaussian mixtures only. Any domain that needs particles, intervals, or sets (e.g. conjunction analysis, RF coverage)? Default: keep the rule; convert at the boundary.
   **Answer (2026-09-02): keep the Gaussian rule.** Mixtures for multimodality; other sources convert at the boundary with a recorded approximation (spoore's assumption ledger applies).
13. **Entity identity.** Is the id assigned in a DRM authoritative through execution? How are real-world assets registered and matched to designed entities (catalog, NORAD id, tail number)? Default: DRM id plus an asset catalog with external-id aliases.
   **Answer (2026-09-02): DRM entity id is authoritative; an asset catalog maps external ids (NORAD, tail number, MAVLink sysid, CCSDS APID) to it; tracks bind to entities through association evidence.**
14. **Schema evolution.** Proto with strict backward compatibility and a review gate, or free-form until v1? Default: strict from P0.
   **Answer (2026-09-02): strict from P0.** Backward-compatible changes only within a major; `buf` breaking-change checks in CI; review gate on proto; explicit `v1`, `v2` packages.

## C. Dynamics and GMAT

15. **GMAT depth first.** FFI to `libGmatBase`, Python API in-process, or native models with GMAT as oracle? Default: API in-process now, FFI spike in P0, native for the hot path later.
   **Answer (2026-09-02): Python API in-process now, `gmat-sys` FFI spike in P0, native Rust models in P3 pinned against GMAT goldens.**
16. **Which GMAT models need parity.** Gravity fields (which files, degree/order), atmospheres (MSISE-00, Jacchia-Roberts), SRP models, third bodies, relativity, tides, SPICE ephemerides? Default: whatever the first DRM uses.
   **Answer (2026-09-02): all of it.** Spherical-harmonic gravity (Earth, Moon, Mars) with third bodies and SRP; atmospheric drag (MSISE-00, Jacchia-Roberts) with packaged space-weather files; relativity, solid and ocean tides, high-fidelity SRP; SPICE kernel reading and ephemeris propagation. Every one gets a golden arc; native ports are prioritized in that order.
17. **Solvers.** Are GMAT's differential corrector, Yukon optimizer and CSALT optimal control needed inside the platform, or only propagation? Default: DC yes, optimizers via the GMAT service only.
   **Answer (2026-09-02): differential corrector as a platform `solve` call; Yukon and CSALT reachable through the GMAT script path.**
18. **Determinism level for the kernel.** Bitwise replay on one architecture (spoore) for lockstep runs, tolerance across architectures; real-time HIL runs replayable only from logged I/O. Acceptable? Default: yes.
   **Answer (2026-09-02): spoore's standard; HIL runs replayable from logged board I/O.**
19. **Step rates.** Target step rate for SIL and HIL (10 Hz, 100 Hz, 1 kHz for GNC)? Changes whether GMAT-in-the-loop is feasible at all versus native models.
   **Answer (2026-09-02): a configuration option per DRM/system, default 10 Hz kernel dynamics with faster loops inside the bound flight software.** The kernel must therefore support per-system step rates (multi-rate scheduling with interpolated sensor outputs), and GMAT-in-the-loop is a supported configuration at the default rate while native dynamics cover the faster settings.
20. **Integrator ownership.** In depth 1, whose integrator: ours (RK/PD/adaptive) or GMAT's? Default: ours, validated against GMAT's.
   **Answer (2026-09-02): ours, validated against GMAT's.** One kernel integrator for every domain and binding; GMAT's integrators are the reference in goldens and in the design-time Python path.
21. **Non-space domains and existing models.** Which first (6-DoF air, ground vehicle, marine, RF links, power, thermal), and are there FMUs, Simulink, or code to reuse rather than write?
   **Answer (2026-09-02): relative motion and RPO first (CW/HCW, full nonlinear relative propagation; contact and docking as a later multibody model), then 6-DoF air vehicles (fixed-wing, rotorcraft).** Ground/marine and RF/power/thermal deferred. No existing model code named yet.
22. **Environment data.** Terrain, atmosphere, space weather, ephemerides: sources, update cadence, licensing, and air-gap packaging.
   **Answer (2026-09-02): versioned data packs, hashed, shipped like the air-gap kit.** A data-pack manifest per deployment; updates are new packs; every run records the pack hash beside the config hash.

## D. Simulation kernel, SIL and HIL

23. **FMI/SSP.** Required on day one for interoperability with existing tools, or later? Default: FMI export in P2, SSP import later.
   **Answer (2026-09-02): FMI export in P2, SSP later.** Our YAML/proto stays the source of truth.
24. **Flight software stack.** cFS, F´, ROS 2, custom? Default: cFS first (CCSDS-native), ROS 2 second.
   **Answer (2026-09-02): NASA cFS first, ROS 2 second.** First port adapters: CCSDS space packets over the cFS software bus (container and Renode), then ROS 2 topics.
25. **Renode targets and time control.** Which MCUs/SoCs and boards? Is deterministic lockstep (Renode virtual time slaved to the kernel) mandatory, or is loosely paced acceptable at first?
   **Answer (2026-09-02): Cortex-M (STM32, nRF) first; lockstep required.** The virtual-time slaving spike happens before the P2 acceptance test depends on it.
26. **Board interfaces.** UART, CAN, Ethernet only, or also SpaceWire, MIL-STD-1553, RS-422, discrete GPIO? The last group needs hardware adapters.
   **Answer (2026-09-02): UART/USB-serial and Ethernet/UDP first; CAN, SpaceWire, 1553, RS-422 and GPIO will probably be needed later, and nothing may preclude them.** Design consequence: the port abstraction in the system definition is bus-neutral from P0 (byte streams, framed messages, and discrete signals as three port kinds, each with declared timing properties such as rate, latency, jitter and determinism), and the edge plugin's I/O layer is a driver interface, not a UART assumption.
27. **Sensor emulation fidelity.** Message-level (a packet that looks like an IMU) or signal-level (bit-accurate register behaviour)? Default: message-level first.
   **Answer (2026-09-02): message-level first; signal-level where Renode's peripheral models provide it.**
28. **Fault injection scope.** Faults at ports (drop, delay, corrupt), in dynamics (parameter changes), in hardware (Renode peripheral faults)? Default: ports and dynamics in P1, hardware later.
   **Answer (2026-09-02): all four scopes.** Port faults (drop, delay, corrupt, duplicate), dynamics and environment parameter/model changes, hardware faults (Renode peripheral faults, board resets, power cycles), and sensor-level faults (bias, noise, dropout, misalignment). All declared in the DRM scenario as timed events and hashed; hardware faults need Renode hooks and edge-node power control.
29. **Ground segment in the loop.** Is the ground system (mission control software, antennas, link scheduling) a system in the SoS config with the same bindings? Default: yes, container-bound.
   **Answer (2026-09-02): yes, a system with the same bindings.** Ground software in a container, antennas/links/contact windows as models, a real station as an edge-bound asset.

## E. Ingestion, edge and security

30. **First protocols.** MAVLink, CCSDS TM/TC, ADS-B, ROS 2, proprietary radios: which two first?
   **Answer (2026-09-02): ADS-B first.** Receive-only, so the first plugin exercises ingestion, labels and signing without a command path; CCSDS TM/TC follows with cFS (question 24) when SIL needs it.
31. **Security framework and accreditation.** NIST 800-53/RMF, CMMC level, DoD IL level? Is there an authorizing official and a real ATO goal, or is "defense-grade" a design posture for now?
   **Answer (2026-09-02): CMMC Level 2 / NIST SP 800-171.** CUI handling drives the boundary design; the development environment (repos, CI, artifact stores, air-gap kit builder) is in scope as much as the product. Consequence: the 110 practices become the checklist behind "defense-grade", with evidence collected from P2, and access control, audit logging, media protection and configuration management are platform features, not deployment afterthoughts.
32. **Classification handling.** Single level per deployment, or multi-level with labels and cross-domain replication (data diodes)? Default: single level per deployment with labels carried anyway.
   **Answer (2026-09-02): single level per deployment; labels carried on every message anyway.** No cross-domain replication built.
33. **Plugin sandbox.** Containers with gVisor/Kata, WASM components, or both by edge class? What edge hardware class (x86 box, Jetson, MCU-class)? Default: containers on x86/ARM; WASM only if MCU-class edges exist.
   **Answer (2026-09-02): containers with gVisor/Kata on x86/ARM Linux-class edge boxes.** Plugins are OCI images with signed manifests; egress allow-listed by network policy.
34. **Identity and PKI.** SPIFFE/SPIRE with an offline CA, or an existing enterprise PKI/CAC? Default: SPIRE.
   **Survey (2026-09-02): the user pointed at https://github.com/secrouter, their SecRouter suite for closed networks.** Relevant components and what each implies:
   - `seccert`: RFC 8555 ACME CA for air-gapped enclaves; two-tier PKI (Root signs Intermediate only), ECDSA P-384, short-lived leaves, hash-chained issuance ledger, `/admin/api/evidence`, optional SecSSO admin login. Candidate replacement for SPIFFE/SPIRE: every service and edge plugin runs a standard ACME client against seccert; the Root is the enclave trust anchor.
   - `secsso`: Authentik OIDC with blueprints, `groups` claim, MFA via `amr`/`acr`, service subjects for machine clients; designed to be dropped for Okta/Entra/Keycloak. Candidate for human identity on viewer, consoles and command authorization.
   - `secdns`, `secproxy`: internal authoritative DNS; nginx front door on the host's FIPS OpenSSL, config generated from the site topology.
   - `secdeploy`: `suite.toml` (pinned bill of materials, components in tiers) + `secsite.toml` (placement, options, users); targets `macos` (eval), `fedora-fips` (production: native hardened systemd services, no containers, fail-closed FIPS preflight), `ubuntu`; deploy-audit SHA-256 hash chain with `secdeploy audit verify`; `secdeploy evidence` pulls every component's `/admin/api/evidence` into one bundle; egress allow-lists generated from topology and cited in the SSP.
   - `secrouter`: the reference CMMC control matrix (NIST 800-171 R2 + selected 800-172), fail-closed FIPS, deny-by-default egress with a classification gate, hash-chained CUI-safe audit with syslog/SIEM forwarding, evidence bundle export, an OpenAI-compatible gateway with an MCP tool gateway (deny-by-default tool allow-list).
   - `secagent`: CMMC page with a Met / Partial / Inherited / Gap legend and a deficiency list; FIPS rules (SHA-256 only, system OpenSSL only, no bundled crypto, UBI9 base images, `NODE_OPTIONS=--enable-fips`); a field test against NASA cFS.
   **Answer (2026-09-02): seccert + secsso, suite conventions.** ACME client in every service and edge plugin; short-lived certs; mTLS with the seccert Root as trust anchor; OIDC from secsso (droppable for an existing IdP) with `groups` and MFA claims for consoles and command authorization. SPIFFE/SPIRE retired.
   Conflicts with the proposal as drafted: Kubernetes + Helm + gVisor/Kata (the suite's production target is native systemd on FIPS Fedora, and containers are avoided so every component links the host's FIPS OpenSSL directly); SPIFFE/SPIRE (the suite uses seccert + ACME); my own control vocabulary (the suite already has a control-matrix format and an evidence pipeline to adopt verbatim). New questions 61–65 below.
35. **Disconnected operation.** How long must an edge buffer and what are the sync semantics on reconnect (full replay, latest-only)? Default: hours of buffer, full replay.
   **Answer (2026-09-02): hours of buffer, full ordered replay on reconnect, edge is capture-only.** No tracking or command authority at the edge while disconnected.
36. **Message signing.** Per message, per batch, or transport-only (mTLS)? Default: per batch plus mTLS.
   **Answer (2026-09-02): per-batch signatures with hash chaining.** ECDSA P-384 with the plugin's seccert-issued key; batch hashes chained per plugin; signatures stored in the log; verify endpoints walk the chain.

## F. Processing and substrate

37. **Redpanda license.** Acceptable, or is a broker mandated by the customer? Default: Redpanda pending legal.
   **Evaluation (2026-09-02) of `influxdata/rskafka`, which the user asked for in answer to this question.** It is a Kafka *client* (MIT/Apache-2.0, pure Rust, v0.6.0 on crates.io, 338 stars, last commit 2026-06-25, "originally used by InfluxDB 3.0 but no longer is"), so it does not replace the broker; it would replace `rdkafka` (librdkafka C bindings) in `spoore-io`. Fit is unusually good: partition-bound clients, no consumer groups, no offset tracking, no transactions, independent write streams per partition, are exactly spoore's ADR-004 discipline (manual assignment, explicit partitions, nothing commits, replay by explicit offset). Costs and risks: maintenance is thin now that InfluxDB dropped it; no idempotent producer (spoore tolerates duplicates by design, ADR-010 merge); TLS is rustls with `ring` or `aws-lc-rs` providers, both bundled crypto and not the host FIPS OpenSSL, but the `transport-tls-no-provider` feature accepts any rustls `CryptoProvider`, and `rustls-openssl` (v0.4.1, active) supplies one backed by OpenSSL 3 with the FIPS provider, which keeps question 63's rule; `rdkafka` by contrast statically bundles librdkafka and OpenSSL unless built with `dynamic-linking`, which is worse for FIPS. Verdict: adopt rskafka as the client behind `spoore-io`'s producer/consumer traits (an upstream PR to spoore, question 2), with `rustls-openssl` as the provider, and pin a fork-ready vendored copy given the maintenance risk. The broker choice stands as a separate question (re-asked).
   **Answer (2026-09-02): Redpanda, pending legal review**, with rskafka as the client. Question 38 (substrate) is answered by question 61: fedora-fips hosts via secdeploy.
38. **Deployment substrate.** Kubernetes assumed? On-prem, cloud, both, air-gapped? k3s at the edge? Default: k8s everywhere, k3s at edges.
39. **Object store and volumes.** MinIO vs customer S3; expected data volumes and retention. Changes sizing and tiering.
   **Answer (2026-09-02): S3 API via MinIO, gigabytes to a few TB.** Single node on the store tier; AGPL acceptable as an unmodified operational dependency outside the open core; a customer S3/GovCloud bucket is a drop-in.
40. **Analytics store.** ClickHouse acceptable, or mandated databases (Postgres only, Elastic)?
   **Answer (2026-09-02): ClickHouse** for analytics and MoE tables; the catalog stays on Postgres as proposed. ClickHouse's TLS must be verified to use the host OpenSSL under the FIPS rule.
41. **Latency targets.** Reuse spoore's (p99 25 ms in-process, 75 ms through the bus) or set per domain? Default: reuse and measure.
   **Answer (2026-09-02): reuse spoore's budgets and re-measure**; the edge-to-core hop gets its own measured line item.
42. **Orbital scale.** Tens of objects (a mission) or tens of thousands (catalog-scale space domain awareness)? Changes partitioning, the hot-track design, and the viewer's entity module.
   **Answer (2026-09-02): tens to hundreds, the mission's own assets and targets.** One shard per orbital regime; catalog ingestion (TLE/OMM) is a later plugin; no conjunction pipeline in scope.

## L. Forks raised by team 1 (2026-09-02, P0/P1 implementation)

72. **`PLATFORM_BODY` frames need an attitude source.** ADR-001 lists `PLATFORM_BODY` among the day-one axes kinds, but `FrameDefinition` carries no attitude, so the frame service rejects it rather than approximate it (correct). Fork: (a) add an additive `attitude_source` to `FrameDefinition` in v1 (a oneof: the entity's attitude stream in the CDM, or a named GMAT attitude model), realized by an attitude service in P2, keeping the frame in the day-one list as "declared now, realized with attitude"; or (b) amend ADR-001 to move `PLATFORM_BODY` off the day-one list until an attitude ADR exists. Recommendation: (a), because sensor footprints (question 50, first-priority viewer feature) need body frames and the schema addition is non-breaking.
   **Answer (2026-09-02): (a), add an attitude source to `FrameDefinition`.** Additive v1 field `attitude_source` (oneof: the entity's attitude stream in the CDM, or a named GMAT attitude model); realized by an attitude service in P2; body frames stay on the day-one list as declared now, realized with attitude.
73. **LVLH axis convention.** The frame service realizes LVLH as Z = -R, Y = -N, X = N x R (in-track). Review finding: this *is* the standard LVLH (X is completed from Y x Z and equals the velocity direction only on circular orbits); an X = V pairing is neither the standard nor buildable in GMAT off a circular orbit. **Ratified by the lead**; `core.proto` now pins it on `AXES_KIND_LVLH`.
74. **Heterogeneous kernel scheduling.** `av-kernel`'s scheduler is generic over one model type. Multi-domain runs (space + 6-DoF air + power) need either trait objects with an erased error type, an enum over model kinds, or per-model actors under the port router. Belongs to ADR-005 (kernel), not decided here; default recommendation: trait objects behind the `DynamicsModel` contract, since bindings (container, Renode, board) are already dynamic.
76. **`FrameDefinition` has no parent pointer** (team 1, M2.3). The viewer's frame graph needs a tree; axes and origin imply a parent (RIC's parent is the reference body's inertial frame; ENU's is the body's fixed frame; a body frame's is the root) but nothing declares it.
