# M2.1: `av-kernel` skeleton and the shared `av-dynamics` crate

**Status:** worker report, not an ADR amendment -- nothing here contradicts or extends
`docs/adr/002-dynamics-contract.md`, which is untouched.

## Summary

Moved `Dopri5` out of `crates/gmat-sys` into a new `crates/av-dynamics` (no GMAT
dependency), defined the `DynamicsModel` trait there per ADR-002's contract, added
`gmat_sys::model::GmatModel` as the GMAT-backed binding (the km<->m / A1MJD<->TAI
boundary), and built `crates/av-kernel`: a TAI-nanosecond clock, a multi-rate scheduler,
Hermite-with-velocity interpolation, and CDM v1 `Trajectory` assembly. The acceptance test
runs the golden LEO arc through the kernel at 10 Hz output sampling and matches GMAT's
propagator to 0.0000 m / 2.430e-8 m/s (golden tolerance: 0.05 m / 5e-5 m/s).

## Design decisions worth recording

**`gmat-sys` depends on `av-dynamics`, not the other way around, and not a re-export from
`av-dynamics`.** `av-dynamics` must build with no GMAT dependency (a native/non-space model
needs the same trait and integrator without ever linking GMAT); `gmat-sys` is the one that
needs `av-dynamics`'s pieces (`Dopri5`, `DynamicsModel`) to implement `GmatModel`. A
dependency edge the other way would contradict "no GMAT dependency." `gmat-sys` re-exports
the module (`pub use av_dynamics::integrate;`) so every existing caller of
`gmat_sys::integrate::Dopri5` needed zero changes.

**`GmatModel` lives in `gmat-sys`, not `av-dynamics`.** The task listed it as its own
section without a `crates/X` header (unlike av-dynamics and av-kernel); since it wraps
`gmat_sys::DerivativeModel` and av-dynamics must stay GMAT-free, `gmat-sys` (which already
links GMAT) is the only crate it can live in without violating that constraint.

**`Scheduler<M>` is homogeneous over one `DynamicsModel` type.** True multi-domain
scheduling needs trait objects or an enum over model types -- a real design decision ADR-002
doesn't make and this task doesn't ask for. The multi-rate requirement is still fully
demonstrated (two systems of the same type at 50 Hz / 10 Hz, driven correctly from one
clock) without inventing that design.

**A small `build.rs` was needed in `av-kernel`, not anticipated up front.** Cargo does not
propagate a dependency's `cargo:rustc-link-arg` (which `-rpath` must be passed as) across a
package boundary, unlike `rustc-link-lib`/`rustc-link-search` (which do, via the `links`
key). `crates/av-kernel/tests/golden_acceptance.rs` linked successfully against
`libGmatBase` (proving the `-l`/`-L` propagation works) but aborted at process start
(`dyld: Library not loaded`) because `gmat-sys`'s own `-rpath` only reaches `gmat-sys`'s own
test binaries. `av-kernel/build.rs` re-emits the same rpath, but only when a GMAT install is
actually found (`GMAT_ROOT`/`GMAT_LIB` or the default path) -- if none is found it emits
nothing, so `av-kernel`'s own library and its GMAT-free tests still build with no GMAT
installed at all. This is documented in the build script itself and in
`crates/av-kernel/README.md`.

## Measurements

**`Dopri5` move: verified bit-identical.** `cargo test -p gmat-sys --test leo_golden --
--nocapture` before and after the move both report `8947 steps, 139 rejected, 63602
GetDerivatives calls`, `|dr| = 0.0057 m`, `|dv| = 6.283e-6 m/s` -- matching ADR-002's
amendment table (5.7 mm, 6.3e-6 m/s) to the last displayed digit. Not one line of the
algorithm changed in the move.

**Kernel acceptance test** (`cargo test -p av-kernel --test golden_acceptance --
--nocapture`, debug build, Apple Silicon): golden arc `leo_1day_jgm2_8x8_sunmoon` (LEO, JGM2
8x8, Sun + Moon, 86,400 s), driven through `Kernel::run` at 10 Hz output sampling
(`output_period_ns = 100_000_000`):

| Measurement | Result |
|---|---|
| Output samples | 864,001 |
| Wall time (debug build) | 24.1 s |
| Position error vs golden `final_state` | 0.0000 m (tolerance 0.05 m) |
| Velocity error | 2.430e-8 m/s (tolerance 5e-5 m/s) |

Smaller than `gmat-sys`'s own continuous-integration golden test (5.7 mm / 6.3e-6 m/s) --
explained, not just noted, in `crates/av-kernel/README.md`: stepping every 100 ms restarts
`Dopri5` with a step size clamped to that 100 ms span each time, so local truncation error
per step is far smaller than a single continuous run's up-to-600-s adaptive steps, at the
cost of ~100x more `GetDerivatives` calls and a correspondingly longer wall time.

**Full suite** (`cargo test --workspace`, default parallel threads): 69 passed (av-cdm 33
unit + 12 integration = the pre-existing 45; av-dynamics 3 new; av-kernel 16 new (lib,
no GMAT) + 1 new (golden acceptance, GMAT); gmat-sys 1 new (model unit test, no GMAT) + 2

## Approximations, deviations and shortcuts -- stated plainly

- **Controls are not routed anywhere.** Every `step` call in the scheduler passes an empty
  control slice. ADR-005 (still Planned) is presumably where real control routing belongs;
  not invented here.
- **`Scheduler<M>` cannot mix `DynamicsModel` types** in one instance (see "Design
  decisions" above) -- a real limitation, not a hidden one.
- **`Trajectory.provenance` and `.config_hash` are left at proto defaults.** Populating them
  (spoore ADR-005 "evidence") is future work.
- **`entity_id` on the built `Trajectory` is just the registered system id.** The kernel
  skeleton has no entity catalog; this is a placeholder, not a claim of equivalence.
- **`GmatModel` wraps only the plain 6-state model, not the 42-state STM binding.**
  `GmatModel::new` panics if handed a `derivative_model_with_stm` result;
  `ModelCapability::Stm` is deliberately absent from `describe()`. Covariance propagation
  through the `DynamicsModel` trait is not attempted.
- **The acceptance test duplicates `leo_golden.rs`'s GMAT setup** rather than sharing code
  across the two crates' test files -- `gmat-sys`'s `tests/` directory isn't something
  another crate can depend on, and the duplication is small and inspectable.
- **`Kernel::run` requires the horizon to be an exact multiple of the output period** (a
  deliberate invariant -- the last sample always lands exactly on `end_tai_ns` -- not a
  best-effort convenience).
- **The `av-kernel` `build.rs`'s GMAT default-path logic is copied by hand from
  `gmat-sys/build.rs`**, not shared via a common crate (Cargo build scripts can't share code
  across packages without a build-dependency crate, which felt like more machinery than two
  small path defaults warranted). If `gmat-sys/build.rs`'s defaults ever change, this copy
  needs updating too -- flagged in both files' comments.
- **`settings_hash` is not itself part of ADR-002's schema** -- `ModelInfo.settings_hash` is
  a plain `string` field in the proto; the hash function and what goes into its input
  `BTreeMap` are this implementation's own choice about how to compute a value for that
  field, not something the proto or ADR-002 prescribes beyond "SHA-256 of the model's
  settings."
