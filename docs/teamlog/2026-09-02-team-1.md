### Defect B-1 (found in baseline review, fixed by the manager before dispatch)

`cargo test --workspace` aborted the process. Root cause: GMAT holds one configuration per
process and is not thread-safe (ADR-002 amendment, `gmat-sys/README.md` "Limits found"), and
libtest runs the two integration tests in `leo_golden.rs` on separate threads of one binary.
Concurrent `Construct` / `Initialize` calls abort inside GMAT's own code. The crate documented
the constraint but nothing enforced it, so the repo's own stated invariant ("`cargo test -p
gmat-sys` must keep passing") only held with a non-default flag.

Fix: `gmat_sys::engine_lock()` — a process-wide `Mutex` guard exported from the crate, held by
each test for its whole body. Poisoning is ignored deliberately (a panicking test leaves GMAT's
configuration dirty regardless; converting that into a second failure hides the first).
Separate test *files* are separate processes that cargo runs sequentially, so any new test file
is safe as long as it takes the guard too.

Verified: `cargo test --workspace` run three times, 2 passed each time, no abort.

### Measurement worth keeping: the A1MJD boundary costs up to 252 ns

Generating the fixture quantified something ADR-001 asserted but never measured. Round-tripping
TAI → A1MJD → TAI loses up to **252 ns** across these epochs (9 ns at 1970, 124–252 ns at modern
dates), because A1MJD is an f64 of days. This is direct evidence for ADR-001's decision to keep
int64 TAI internally and confine A1MJD to the GMAT adapter — the boundary itself is the lossy
part, and it is now pinned by a test rather than assumed.

Two float-precision traps were hit and are recorded in the generator's comments so the next
person does not rediscover them: fixed-precision `{:.17}` formatting of an f64 does **not**
round-trip (it shifted values by one ULP, ~157 ns), and recovering an f64 from decimal text is
parser-dependent at the last bit — `serde_json`, Rust's `str::parse` and Python's parser do not
always agree on the final ULP. The fixture's contract is therefore the **integer** fields, which
are exact; `a1_mjd` is asserted only within the documented f64 floor. Demanding bit-exact f64
agreement across three parsers would over-specify beyond anything the CDM guarantees.

### Escalation E-6: `Propagator.Step(dt)` shows a MaxStep-dependent divergence

Worker F reported that `Scenario.propagate(step=...)` conflates the external `Step()` chunk size
with the sampling cadence, citing ~1e7 m divergence. The manager investigated directly rather
than accepting it. Findings, stated with their limits:

- With gmatviz's own defaults (`step=60`, `MaxStep=300`) the result is **exactly** invariant to
  chunk size: 60 s, 300 s, 600 s, 900 s, 1800 s and 3600 s chunks all agree to **0.000 m**. The
  four examples are in the safe region.
- One reproducible anomaly survives: `Step(3600)` with `MaxStep=2700` diverges by **701 km** from
  the same span taken in smaller chunks, while `Step(3600)` with `MaxStep=300` is exact.
- **Two of the outliers in the manager's first sweep were his own harness's bug**, not GMAT's:
  it computed `n = round(total/chunk)` and so under-propagated when `chunk` did not divide the
  total. That accounts for them exactly (900 s of missing propagation at ~7.3 km/s = 6570 km,
  against 6573 km measured). Recorded because it nearly became a false finding.
- A clean rule was **not** established; `dt > MaxStep` alone does not predict it.

This needs a dedicated investigation before anything relies on `Step()` with a large `dt`.
`gmat-service` sidesteps it by driving the raw `Propagator` and chunking at
`min(sample_interval_s, MaxStep)`. Not a blocker today; a real trap for P2's SIL work.

### Escalation E-10: two defects in ADR-005 section 6's EBNF

Found by implementing the grammar exactly as written rather than fixing it silently:

1. **`range(a, b)@time` is not parseable.** The grammar's `call := name '(' [expr (',' expr)*] ')'`
   has no `['@' time]` suffix — only `ref` does. So `@` after a call is `TrailingInput`.
2. **Comparisons do not exist in the grammar.** There is no `<`/`>`/`<=`/`>=` production in
   `expr`/`term`/`unary`/`primary`, and `<` is not even lexable — yet **ADR-005 §6's own worked
   example is `duration(range(a, b) < 100 m)`**. Both `duration` and `range` are `UnknownFunction`.

The ADR's illustrative example cannot be parsed by the ADR's own grammar. Needs an amendment
adding a comparison production and a `@time` suffix on calls (or a corrected example). Not
decided by the team.

### M12.2 epoch write-back — accepted

`DerivativeModel::sync_spacecraft_epoch_a1mjd` sets `DateFormat = A1ModJulian` then `Epoch` as a
string (GMAT refuses a numeric `SetField` on `Epoch`); `f64` formatting round-trips losslessly, so

longitude at Earth's rotation rate.

Cartesian state (or of neither) and would read identically at any epoch — they could never catch a
missing write-back. The worker chose **Earth-fixed longitude**, and proved its epoch sensitivity
with a stale-epoch control: holding position fixed but using the construction epoch moved longitude
by **0.985573 deg**, against a predicted solar/sidereal residual of
`360 x (86400/86164.09 - 1) = 0.9856 deg`. Measured against a genuine GMAT `ReportFile`:
**longitude 5.049e-8 deg, latitude 1.474e-9 deg.**

### The finding that matters most: we now knowingly disagree with GMAT

M21.4's required pin had two branches — match GMAT's own covariance report if GMAT can produce
one, else match `R P Rᵀ` from GMAT's reported rotation. GMAT **can** report
`OrbitErrorCovariance` in `EarthFixed`, so the first branch was live. The worker read GMAT's own
`OrbitData::GetCovarianceRmat66` and found it builds only the **block-diagonal** `[[R,0],[0,R]]`
transform: it never calls `GetLastRotationDotMatrix()`, so GMAT's covariance report in a rotating
frame **omits the `Ṙ` coupling entirely**.

Measured against our implementation: the position block agrees to **8.674e-17** relative, while
the cross and velocity blocks disagree by **1.258e-6** and **9.171e-11** — linear and quadratic in
Earth's rotation rate respectively, which is exactly the signature of a missing `Ṙ` rather than
noise. The worker therefore pinned the "otherwise" branch (`R P Rᵀ` from GMAT's own reported
rotation, met at **9.626e-18** relative against a 1e-12 bound) and added a regression test that
asserts the disagreement *exists*, so a future change back to block-diagonal fails.

This is worth the lead's attention because "goldens against GMAT are the proof for every dynamics
model" is a binding rule, and here the correct answer is not GMAT's. It is recorded rather than
quietly absorbed. See E-28.

### The closed loop, expected before measured

Quaternion-feedback PD, `τ_k = kp·qv_k + kd·ω_k`, gains sized for **exact critical damping**
(`kp = kd²/2Jz`; kd=5.0, kp=0.25, Jz=50) giving `τ = 2Jz/kd = 20 s` and

fixture before the run. At t = 300 s = 15τ the deterministic residual is `0.2 × 16e^(−15) ≈
9.8e-7 rad`, **below** the star tracker's 1e-5 rad noise floor — so the measured error is
expected to be noise-dominated and never exactly zero. Measured: **1.2579e-4 rad**, ~12.6× the
single-sample floor because noise forces the loop continuously through its closed-loop bandwidth
rather than once at the end, and a >1500× reduction from the 0.2 rad start. No overshoot at any
of 14 checkpoints. I verified the loop reads **measured** attitude, never truth:
`q_err = target_q⁻¹ ⊗ measured_q` in `controller.rs`.

A real finding surfaced while authoring it and was fixed at the source rather than absorbed: with
a 1 Hz kernel step the zero-order-hold torque deviated 2.9× from the continuous ideal by t=300 s.
The fix was raising the step rate to 10 Hz, not widening a bound.

## Command state names: the lead's paraphrase vs the enum (manager, 2026-09-07)

The M25 dispatch described the command state machine as "proposed, approved, dispatched,
acknowledged, executed". The actual enum in `proto/altavista/v1/command.proto` is:

`COMMAND_STATE_{PROPOSED, CHECKED, AUTHORIZED, DISPATCHED, ACKED, REJECTED, EXPIRED, FAILED}`

Three differences that matter for M25.2, which is built entirely on this machine: **CHECKED** has
no counterpart in the paraphrase and would have been dropped; **AUTHORIZED** and **ACKED** were
paraphrased as "approved" and "acknowledged"; and **"executed" is not a state at all** — it is an
*ack level*, `ACK_LEVEL_ASSET_EXECUTED`, a separate axis from the state machine. A worker briefed
from the paraphrase would have emitted a four-state machine with an invented fifth state and no
`CHECKED`, and every `EVENT_KIND_COMMAND_TRANSITION` would have been wrong.

Caught by reading the proto before briefing rather than transcribing the dispatch. Recorded at the
lead's own request. This is the same class as my own E-18 briefing error (I once told a worker only
three fault-target kinds existed when a fourth was declared with a comment describing it) and the
same class as the four instrument failures beside question 164: **a description of the artifact is
not the artifact.** The standing habit that catches it is cheap — before briefing anything typed,
grep the proto or the source for the real names.

## `large_enum_variant`: boxed, not suppressed (manager, 2026-09-07)

M21.3 hit clippy's `large_enum_variant` when `ConstantAccelSpec` shrank (`[f64;6]` -> `Vec<f64>`)
and crossed the size-ratio threshold against `GmatSystemSpec`. It added
`#[allow(clippy::large_enum_variant)]` on `BindingPlan`, disclosed, on the argument that boxing
would touch ~25 call sites for a cosmetic concern on a short-lived enum.

M25.2 hit the same lint from the other direction — new spec fields grew a variant — and **fixed it
by boxing three `PacketCodec` fields** rather than widening the suppression.

**The boxing is the precedent to follow.** A suppression is a standing claim that the lint is
wrong here, and it silently covers every later change to the same enum: M25.2's regression would
have been invisible had the `#[allow]` still been load-bearing at that site. Boxing costs call
sites once; an `#[allow]` costs the signal permanently. Where the two are close, prefer the fix.
The M21.3 suppression stands as recorded history with its reasoning, but it should not be cited as
the pattern.

### Question 157, fifth and sixth occurrence

All three workers this round stopped without a final report at the point they decided to
*wait*: the harness ends a subagent's turn when it says it will wait for a notification, and
nothing wakes it. Two of the three had already produced their artifacts, so the incremental
REPORT.md rule saved the work exactly as intended -- I finished the runs and the re-pin myself
from their reports. **The fix is in the brief, not the worker**: give a blocking shell command
(`while ps -Ao command | grep -E "cargo test|pytest" | grep -v grep >/dev/null; do sleep 30;
done`) and say explicitly never to end a turn waiting for a notification. The third worker,
briefed that way, ran for 2.7 hours and returned a full report with gates.

### Open, for the lead

- A command dispatched from `Scenario.events` is carried by the router before the first output
  tick, so its records carry `sequence = 0` and `PortTrafficLog.records`'s
  `(sequence, instance, port)` order is not epoch-monotonic. Replay keys on `tai_ns`, so nothing
  is broken; recorded because the sort order is a wire contract.
- The cFS image cannot be reproducible as built: cFE's own `generate_build_env.cmake` stamps
  `date +%Y%m%d%H%M` into `CONFIGDATA` unless `BUILDDATE` is set, and the Dockerfile sets
  neither it nor `BUILDUSER`/`BUILDHOST`. Pinning those three would stop the digest drifting on
  every cache-evicted rebuild, but it changes the image once more, so it is recorded as a
  recommendation rather than done.
- Replaying a **native model** is not generally byte-identical (a model reports applied commands
  and measurements a frame replay cannot reconstruct). Replay is scoped to container-bound
  instances by default for exactly that reason; naming a model instance explicitly is supported
  and is what makes the Docker-free tests possible.

  today's 182 / 768 / 436). Left for the lead, who owns that file.
