# `goldens/`: generator, reason, tolerance and residual for every committed golden

N6 deliverable 2 (`docs/native-dynamics-plan.md`, "Selection, goldens and the C ABI hedge"):
"every golden's generator script, reason, tolerance and residual tabulated in
`goldens/README.md`." This file did not exist before this task; it is created here, once, and
should be kept current by whichever task next changes a golden (regenerates one, adds one, or
moves a tolerance into one) rather than left to drift.

ADR-002's own goldens rule (`docs/adr/002-dynamics-contract.md`, "Goldens") is the frame for all
of this: `goldens/` holds GMAT reference arcs generated by an explicit command with a recorded
reason, never regenerated by a test; every golden records the GMAT version, data-pack hash,
script hash, settings and tolerance. Charter question 222(d) restates it for this track: "every
force gets a golden with its generator script, reason, tolerance and residual; a force that
misses its golden records the residual, never a loosened tolerance." Every row below comes from
one of three places, and each row says which: the golden file's own JSON, the test that reads
it, or (for this track's own N1-N5 work) the "Goldens" table in the relevant round's status
section of `docs/native-dynamics-plan.md`. Nothing here is invented and nothing is rounded; where
a number could not be established from a committed source, the cell says so and names where the
number would have to come from.

There are 24 `.json` goldens directly under `goldens/` (`goldens/sweep_results_json/` is a
separate directory of `av-sweep` fixture output, not an ADR-002 GMAT-pinned golden in this
sense, and is not tabulated here).

## Two things to read before the table

**The two-body golden is the one documented exception, and it is not ADR-002's fifth
amendment.** `twobody_analytic.json`'s own `reason` field states this directly: a pure two-body
arc (spherical-harmonic degree/order (0, 0), point-mass only) has an exact closed-form solution
(Kepler's equation), so it is proved against that analytic reference rather than against GMAT.
This is explicitly **not** ADR-002's fifth amendment (which is about a GMAT rotated-covariance
report omitting a rotation-rate term, `docs/open-questions.md` question 150) — it is a different,
narrower thing: the one golden ADR-002's own goldens rule does not apply to, because the
reference it is pinned against is a closed form, not a GMAT run. Every other force in this
crate still gets its golden against GMAT.

**The Jacchia-Roberts / M5 residual stands recorded, at no loosened tolerance, per question
230.** `leo_1day_jgm2_8x8_sunmoon_drag_srp.json` (the M5 arc) was never itself asserted against
by the native model — its own recorded 0.05 m pins the `gmat-sys` shim path, a different
implementation entirely. The native model's own residual on that identical arc is **68.32 m
position / 0.0803 m/s velocity**, against the shim path's 7 mm / 3 mm/s
(`docs/native-dynamics-plan.md`, round 2's "What the numbers say" and round 3's "Jacchia-Roberts:
what the decomposition says, and what it does not"). Round 3 decomposed the disagreement to a
definitive per-species fit (nitrogen −4.515e-4, helium −1.492e-3, atomic oxygen +6.743e-4,
explaining 90.7% of the residual's RMS) without locating a single defective line; the remaining
lever (instrumenting GMAT's own `rho_high` term by term) needs a local GMAT build and first needs
someone to verify `third_party/gmat-src`'s relationship to the shipped `libGmatBase.dylib`, which
nobody has done. No tolerance anywhere in this crate was loosened to accommodate this — the
number is carried in `crates/av-orbital/tests/drag_srp_m5.rs`'s own doc comment and asserted
against a measured-plus-margin bound (110 m), not against a tightened golden.

## The six goldens question 230 named as carrying no tolerance in the file

Round 3's own inventory (`docs/native-dynamics-plan.md`'s round-3 open items, ratified in
`docs/open-questions.md` question 230) named the goldens whose tolerance lived only in a Rust
test constant, never in the golden file itself — round 1's own review lesson recurring ("a golden
that inherits a default tolerance pins nothing") in files this track had not opened:
`covariance_bodyfixed_leo_2h`, `ground_contact_gmat`, `leo_1day_jgm2_8x8_sunmoon_planetodetic_lon`,
`leo_1day_jgm2_8x8_sunmoon_rmag`, and the three `expr_*` goldens (seven files by name, though
question 230's own text calls them "six" — an inconsistency in that text, not resolved here,
since it is not this task's file to edit).

All seven now carry the tolerance in the file, as a `golden_comparison_tolerance` object
(`value`, `unit`, `source`), each written by the golden's own generator and each read from the
file by the test that asserts with it. A reader that finds the field missing fails loudly and by
name rather than falling back to a default, which is the whole point: a golden that inherits a
default tolerance pins nothing.

The same regeneration separated two things that had been conflated. A golden's `reason` now
states why the golden exists and is fixed in its generator, while the regeneration's own reason
goes in `golden_regeneration_reason` beside it. Before this round every regeneration overwrote
`reason` with that run's note, which is how the three `expr_*` goldens came to share one
identical M9.3 sentence that was true of only one of them; each now carries its own.

Two of the seven have a reader this track may not edit: `covariance_bodyfixed_leo_2h`'s
assertion lives in `crates/gmat-sys/tests/convert_rotation.rs:226` and
`leo_1day_jgm2_8x8_sunmoon_planetodetic_lon`'s in `crates/gmat-sys/tests/epoch_writeback.rs:209-210`,
and `crates/gmat-sys` is outside this track's isolation boundary. Both constants equal the value
now recorded in the golden, so nothing disagrees; but for those two the tolerance sits in the
file and is still not read from it, and a follow-up inside `gmat-sys` is what closes them.

**Footnote on the three `expr_*` goldens' `reason` field and their generator.** Their committed
`reason` field is identical, verbatim, across all three files, and describes M9.3's CDM-events
change (question 95) rather than each golden's own specific worked example — the Reason column
above instead summarises each generator's own module doc comment, which does describe the
individual case; this is recorded here rather than silently worked around, per this task's own
brief. Separately, and worth documenting because it has never been documented anywhere before
this file: **the three `expr_*` goldens have no Python generator.** Every other golden in this
table is produced by a `goldens/gen_*.py` script; these three are produced by
`crates/av-kernel/examples/gen_expr_goldens.rs`, a Rust example run with `cargo run -p av-kernel
--example gen_expr_goldens -- --reason "..."`. This is legitimate, not an oversight: what these
three goldens pin is not a GMAT-generated trajectory but the platform's own expression-language
evaluator's output (an `Objective`/`MeasureOfEffectiveness` score) for a small, entirely
GMAT-free `"native.constant_accel"` DRM checked by hand against a closed-form constant-
acceleration solution — there is no GMAT reference to call out to for "what should this
expression evaluate to", so a Rust example that runs the same evaluator the crate under test
runs is the only thing that could generate this fixture. It is the evaluator pinning itself, the
same category of exception `twobody_analytic` is for the propagator (see "Two things to read"
above), stated here for the first time.
